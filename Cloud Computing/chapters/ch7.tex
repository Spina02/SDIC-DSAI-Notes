\chapter{Data Cloud and Cloud Security} \label{ch:data_cloud}

Previous chapters covered how cloud infrastructure is built (virtualization, containers) and measured (benchmarking). This final chapter focuses on its main purpose: storing and protecting \textbf{data}. It firstly traces the storage evolution, from traditional systems to cloud object storage, with a deployment example (Nextcloud), and then covers cloud security at different infrastructure levels.


\section{Cloud Storage and Its Predecessors} \label{sec:cloud_storage}

\begin{definitionblock}[Cloud Storage]
    \bfit{Cloud storage} is a service model in which data is maintained, managed, and backed up remotely and made available to users over a network, typically the Internet.
\end{definitionblock}

Users generally pay for cloud storage at a per-consumption, monthly rate, in line with the pay-as-you-go model of \cref{sec:defining_cloud}. Although the cost per gigabyte has been driven down radically, providers have added operating expenses that can make the technology more expensive than users expected, and security remains a concern among users. Providers have tried to address those fears by building capabilities such as encryption and authentication into their services.

\vspace{-1.3em}

\begin{minipage}{0.68\textwidth}
    The motivation for the model is the \textbf{data efficiency gap} sketched in \cref{fig:efficiency-gap}: driven by the explosion of data and by the growth of mobile devices, the amount of data grows faster than the capacity to manage it, and the difference between the two curves widens with scale. Cloud storage aims to close this gap by improving scalability (both up and out) and security, improving performance, simplifying storage management, providing on-demand access, and coping with unstructured data.
\end{minipage}%

\subsection{Traditional Storage Architectures}

\vspace{-0.5em}

\begin{minipage}{0.68\textwidth}
    Before the cloud, storage was organized in two main ways:

    \medskip

    \begin{itemize}
        \item \textbf{Block storage}: exposes \emph{volumes} made of blocks that can be read and written individually, and is accessed through protocols such as Fibre Channel or iSCSI. It is local to the machine using it, offers low latency and high IOPS, but has a limited size (below 1\,PB), and it is complex to expand and expensive.

\begin{warningblock}[Limitations of traditional storage]
    Traditional storage struggles to scale with the number of files, users, geographic distribution, and data volume. It lacks a central naming, locking, and a unified file store. Data is split into separate file systems and volumes, so applications must track both volumes and locations.
\end{warningblock}

These limitations motivate the two approaches examined next: distributed file systems, which keep the file abstraction but spread it over many machines, and object storage, which replaces it.

\section{Distributed File Systems} \label{sec:dfs}

\begin{definitionblock}[Distributed File System]
    A \bfit{distributed file system} (DFS) is a file system shared by many distributed clients. The resources (files and directories) on a particular machine are local to it, while resources on other machines are remote; a DFS is the basic layer for many distributed systems and applications. It provides a service for clients through the normal set of file operations (create, read, and so on), and its servers allow clients to operate on resources that reside on the servers themselves.
\end{definitionblock}

Ideally, clients access remote files as if they were local. Clients, servers, and storage can be distributed across machines in various configurations: servers may have dedicated machines, or be co-located with clients. 

\medskip

A distributed file system (DFS) should possess several important properties across different areas:

\smallskip

\begin{itemize}
    \item \textbf{Transparency}: the client cannot tell \emph{where} a file is located (location); a file can move to another server without the client noticing (migration); multiple copies of a file may exist (replication); and multiple clients may access the same file (concurrency).
    \item \textbf{Flexibility}: servers may be added or replaced, and multiple file system types are supported.
    \item \textbf{Dependability}: consistency is put under stress by replication and concurrency; security is complicated by users having different access rights on the clients sharing files, and by network transmission; and fault tolerance must deal with server crashes and with the availability of files.
    \item \textbf{Performance}: requests can be distributed across servers, enabling higher capacity and scalability.
    \item \textbf{Caching}: network traffic is reduced by retaining recently accessed disk blocks in a cache, so that repeated accesses to the same information are handled locally. If the required data is not cached, a copy is brought from the server to the user and the accesses are performed on the cached copy.
\end{itemize}

\medskip

Caching implies that each file has one master copy residing at the server machine, while copies of (parts of) the file are scattered across different caches. This gives rise to the \textbf{cache consistency problem}: keeping the cached copies consistent with the master file.

\subsection{The Network File System}

\begin{minipage}{0.49\textwidth}
    The Network File System (NFS) is the classic example. On the client, an application issues system calls that reach a \emph{virtual file system} (VFS) interface, which dispatches them either to a local file system that accesses the local disk, or to the NFS client. The NFS client forwards the request over the network to the NFS server, which in turn hands it to the VFS interface of the server and to the file system managing its disk. Because of the VFS layer, the application does not need to know whether a file is local or remote, which is precisely the transparency sought above.
\end{minipage}%

\subsubsection{Case Study: The Google File System} \label{subsec:gfs}

The \textbf{Google File System} (GFS) was developed by Google to handle the massive amounts of data generated by its search engine. Its motivation is to offer one single distributed file system that stores big data reliably and allows its parallel processing. Its design rests on a set of assumptions that differ deliberately from those of a general-purpose file system:

\begin{itemize}[noitemsep]
    \item components are inexpensive and often fail;
    \item files are large (millions of files of 100\,MB or more);
    \item large streaming reads, small random reads (500Mb/s read/write load), and large sequential writes;
    \item multiple users append to the same file;
    \item high bandwidth is more important than low latency.
\end{itemize}

GFS does not adhere to standards like POSIX, but offers a familiar interface (\texttt{Create}, \texttt{Delete}, \texttt{Open}, \texttt{Close}, \texttt{Read}, \texttt{Write}) with two additional operations: \emph{snapshot}, a low-cost copy of a whole file using a copy-on-write operation, and \emph{record append}, an atomic append operation.

\smallskip

\begin{minipage}{0.48\textwidth}
    Files are split into fixed-size \textbf{chunks} of 64\,MB, stored on \textbf{chunk servers} and replicated on multiple of them. A single \textbf{master server} keeps the metadata, accepts the requests on metadata, and performs most of the management activities, while the chunk servers keep the chunks and accept the requests on chunk data. Clients interact with the master only to obtain chunk handles, and with the chunk servers for the actual reads and writes; there is no explicit caching.
\end{minipage}%
\hfill
\begin{minipage}{0.49\textwidth}
    \centering
    \includegraphics[width=\textwidth]{assets/fig43.png}
    \captionof{figure}{Google File System architecture.}
    \label{fig:gfs-architecture}
\end{minipage}

\smallskip

\cref{fig:gfs-read} illustrates file reading in GFS. The application provides a file name and byte range to the GFS client, which maps them to a chunk index and queries the master. The master returns the chunk handle and replica locations. The client then requests the data directly from a chunk server and delivers it to the application. The master only manages metadata; all data transfer is handled between client and chunk server.

\section{Object Storage} \label{sec:object_storage}

A traditional storage system exposes a file system interface through the OS, handles millions of files on a single site, and costs dollars per GB. \textbf{Object storage} instead exposes an HTTP API directly accessible by the applications, handles billions of files, is geo-distributed, and costs cents per GB.

\vspace{-0.7em}

\begin{figure}[H]
    \centering
    \includegraphics[width=0.7\textwidth]{assets/obj-fs.png}
    \caption{Traditional storage compared with object storage.}

    \vspace{-0.7em}

    \label{fig:traditional-vs-object}
\end{figure}

\vspace{-0.7em}

Object storage is offered as public cloud services, such as Amazon S3, Google Storage (not Google Drive), and HP Cloud Object Storage, and can also be deployed as an object storage system, for example the OpenStack Object Storage System (\emph{Swift}) or CEPH. Swift is the world's most popular object storage system: it powers extremely large storage clouds, is 100\% open source (Apache 2), and has a rich ecosystem of tools and applications, with more than 180 developers.

\vspace{-0.7em}

\subsection{Objects and Metadata}

\begin{definitionblock}[Object]
    An \bfit{object} is a logical unit of storage made of an identifier (ID), the application data, the metadata (which includes the block allocation and the length), and a set of attributes accessible by the users. Objects have file-like methods (\plaintt{open}, \plaintt{close}, \plaintt{read}, \plaintt{write}), and in short \[\text{object} = \text{file} + \text{metadata}.\]
\end{definitionblock}

\bfit{Metadata} describes an object: it identifies, characterizes, and specifies the object, records where and when it is used, and manages access permissions. Objects can have different attributes, which can be added, removed, or changed at any time; all metadata is stored with the object as extended attributes and can be indexed. There are two types of metadata: \emph{system} metadata, managed by the storage system, and \emph{custom} metadata, defined by the user.

\begin{observationblock}[FITS files and astronomical image metadata]
    The Flexible Image Transport System (FITS) is the standard digital file format in astronomy, designed for storing, transmitting, and processing complex data sets such as multi-dimensional arrays, tables, or non-image data like spectra and catalogs. FITS files are \emph{self-descriptive}: all metadata about the observation is stored in the file header. When stored as objects, FITS files are a natural fit for object storage: archives must be cost-effective, online, and metadata-rich. Each \plaintt{image.FITS} object includes both system metadata (file class, name, creation time, ...) and custom metadata (observation details, telescope information, ...):
    %
    \begin{minipage}[t]{0.47\textwidth}
        \begin{codeblock}[language=bash, basicstyle=\ttfamily\scriptsize]
File class = image
Filename   = image.FITS
Created    = Oct  3, 2018 13:29:59
Last modified: Oct 10, 2018 11:00:00
...
        \end{codeblock}
    \end{minipage}\hfill
    \begin{minipage}[t]{0.47\textwidth}
        \begin{codeblock}[language=bash, basicstyle=\ttfamily\scriptsize, firstnumber=5]
OBJECT   = 'SZ_Lyn '
TELESCOPE = 'SVAS '
OBJCTRA  = '08 09 36'
OBJCTDEC = '+44 28 18'
...
        \end{codeblock}
    \end{minipage}
    This structure ensures that both the image and its rich metadata are permanently and reliably archived for discovery and analysis.
\end{observationblock}

Since metadata is indexed, it can be \emph{mined} both to identify relevant objects and to analyze characteristics of the data stored. \textbf{Content discovery} refers to finding specific files or objects based on their metadata (e.g. ``all files owned by a user and created after a certain date''), whereas \textbf{metrics gathering} involves collecting statistical information about groups of objects (e.g. ``what is the size distribution of files?''). These capabilities enable both efficient search and aggregate analysis of stored data.

\subsection{Accessing Objects with HTTP}

\begin{minipage}{0.56\textwidth}
Objects have a 64-bit unique ID and exist in a \emph{flat namespace}. Storage requests use HTTP RESTful APIs (or the Swift client) as in \cref{sec:communication_protocols}: the client sends a request to a server, which stores and replicates the data for durability and availability, and which answers with a response stating whether the request succeeded. A request consists of the HTTP verb, authentication, a storage URL (\textbf{SURL}), and optional metadata. In Swift, requests reach a \emph{proxy} that fronts the storage nodes, possibly behind a load balancer.

\section{A Data Cloud in Practice: Nextcloud} \label{sec:nextcloud}

To see how these concepts combine in a real service, the course uses a cloud storage solution based on \textbf{Nextcloud}, which can be deployed on premises or in the cloud, is customizable and scalable, and is advertised as returning control of the data to the user.

\subsection{Capabilities and Architecture}

A \textbf{Cloud Storage} service maintains and backs up data remotely, making it accessible to users over a network (typically the Internet). Usage is generally charged per consumption, often monthly. While storage costs per gigabyte have dropped, additional operating expenses remain, sometimes making the service costlier than expected. Security is a common concern, so providers implement features such as encryption and authentication.

\smallskip

The capabilities of this kind of service are:
\smallskip

\begin{itemize}[itemsep=0.4em]
    \item \textbf{Cloud File Storage}: Users can upload, download, and delete files with full permissions in their private directories. The system supports managing files in a scalable, distributed storage backend to ensure high availability and durability.
    \item \textbf{User Management}: Groups can be created to manage permissions for multiple users at once. Essential features include login, logout, and signup functionalities for users.
    \item \textbf{Easy to use Web GUI}: Provides a simple and intuitive web interface that is accessible and easy to use on any device, allowing users to manage and browse their files conveniently.
    \item \textbf{Security}: Includes server-side encryption, encrypted communication between client and server, brute-force attack mitigation, and customizable security policies for both the OS and passwords.
    \item \textbf{Scalability}: Designed for easy horizontal scalability and includes load balancing to distribute workload across servers and prevent bottlenecks.
    \item \textbf{Multiple access protocols}: Supports different access methods such as native clients and object storage APIs, to accommodate diverse user preferences and integration needs.
\end{itemize}
\smallskip


Its architecture uses a distributed file system that replicates data across multiple servers for high availability and durability. Clients access files via a RESTful API, performing CRUD operations using standard HTTP methods. Typically, a master server manages file system metadata, while several slave servers store the actual data.

\smallskip

The service is made of three kinds of components. The \emph{server and application code} comprises the PHP runtime and a web server; a \emph{database} (MySQL/MariaDB or PostgreSQL) stores everything except the binary files, such as users, shares, and settings; and the \emph{storage} holds the user-uploaded files, their versions, the trash bin, and the previews.

\begin{itemize}
    \item \textbf{Load balancers}: two load balancers built with HAProxy, a virtual IP, and Keepalived distribute the requests over the web servers.
    \item \textbf{Web servers}: four servers running Apache with \plaintt{mod\_php} or \plaintt{php-fpm} (PHP 7.1 or newer recommended), each with a local LDAP slave.
    \item \textbf{Authentication and file storage}: authentication is provided by LDAP, while the files reside on NFS or on an object store (\cref{sec:dfs,sec:object_storage}).
    \item \textbf{Caching and locking}: Redis servers provide a cache and high-level file locking, reduce the load on the database, and can use different servers for locking and for caching.
    \item \textbf{Database}: a master-slave cluster (MySQL Galera recommended) with a database load balancer, based on MaxScale or HAProxy, that sends the writes to the master and the reads to the slaves.
\end{itemize}

    \item \textbf{Portainer}: a management tool for Docker environments, easy to set up;
    \item \textbf{Grafana}: an analytics and visualization platform that allows users to query, visualize, and monitor data from multiple sources in real time, at the price of requiring configuration. The slides show a Nextcloud dashboard with, among others, availability, CPU load, database size, shared links, and recent log entries.
\end{itemize}

\section{Cloud Security} \label{sec:cloud_security}

\subsection{Introduction and General Considerations}

A user who moves to the cloud and wants some privacy faces a first, reassuring fact: many of the security problems of non-cloud environments still apply, and the classical countermeasures remain valid. On top of them, the cloud adds new problems, because resources are shared, outsourced, and managed by a third party. The security of a cloud can be organized in the layers of \cref{fig:cloud-security}: \emph{information security of the infrastructure} (at network, host, and application level), \emph{information security of the data} (encryption, data masking, content protection), and \emph{security management and monitoring services} (monitoring of health, security events, and threats; management of ACLs, vulnerabilities, patches, and configuration).

    \centering
    \includegraphics[width=0.55\textwidth]{assets/fig49.png} % TODO: check filename against ch7_old.tex
    \caption{Layers of cloud security.}
    \label{fig:cloud-security}
\end{figure}

\vspace{-1em}

The discussion focuses on public clouds, and starts from the observation that different cloud service models (\cref{sec:service_deployment_models}) provide different levels of security. Whatever the model, a cloud must provide auditing, data integrity, e-discovery for legal compliance, privacy, recovery, and regulatory compliance.

\begin{definitionblock}[Security boundary]
    The \bfit{security boundary} separates the responsibilities of the client from those of the vendor: it answers the questions of who is responsible for a particular security mechanism, and of where the boundary lies between the responsibility of the service provider and that of the customer.
\end{definitionblock}

The Cloud Security Alliance (CSA) is an industry working group that studies security issues in cloud computing and offers recommendations to its members. The boundary moves with the service model, as \cref{fig:xaas-boundaries} shows: the layers of the service stack (from the data centre with its mechanical and electrical facilities, through networking and firewalling, physical servers, the virtualization layer, and the operating systems, up to the infrastructure software, the hosted application, and the client devices and people) are covered by the provider in an increasingly large portion as one moves from IaaS to PaaS to SaaS. A consequence is that the security level of a platform is reduced to that of the most vulnerable application running on it, which is why applications should be isolated with VMs and containers.

    \caption{Service layers and XaaS security boundaries.}
    \label{fig:xaas-boundaries}
\end{figure}

\vspace{-1em}

Multi-tenancy (\cref{sec:service_attributes}) adds a further requirement: different customers must be isolated, their data segmented, and their services identified and isolated. A multi-project approach, such as the OpenStack \emph{tenants}, is one way to achieve it.

Before approaching the cloud, an organization should therefore go through a few steps:

\begin{enumerate}
    \item determine which resources (data, services, or applications) are planned to move to the cloud, and how sensitive they are to risk;
    \item evaluate the risks, namely loss of privacy, unauthorized access by others, loss of data, and interruptions in availability;
    \item determine the risk associated with the cloud type for a resource, and consider the cloud service model that will be used;
    \item if a provider has already been selected, evaluate its system to understand how data is transferred, where it is stored, and how to move data both in and out of the cloud.
\end{enumerate}

\subsection{Common Risks and Challenges}

The most common security risks and challenges associated with cloud computing are the following.

\begin{itemize}
    \item \textbf{Data breaches}: an unauthorized party gains access to sensitive data stored in the cloud, through hacking, phishing, or social engineering.
    \item \textbf{Data loss}: data stored in the cloud is accidentally deleted, corrupted, or otherwise lost, because of hardware failure, software bugs, or human error.
    \item \textbf{Account hijacking}: an unauthorized party gains access to a user's cloud account, through phishing, social engineering, or weak passwords, and can then steal data, delete files, or perform other malicious activities.
    \item \textbf{Insecure APIs}: the APIs used to access cloud services are not properly secured, because of weak authentication, lack of encryption, or other vulnerabilities, and can be exploited to reach sensitive data.
    \item \textbf{Insider threats}: an authorized user of a service intentionally or unintentionally causes harm, for instance a disgruntled employee, a careless user, or a user tricked by an attacker. They are hard to detect and prevent, since the attacker already has legitimate access.
\end{itemize}

\subsection{Infrastructure Security}

Security of the infrastructure is analysed at three levels, from the most basic to the highest.

\textbf{Network level.} Security at the network level concerns the infrastructure connecting the cloud servers to the Internet, with firewalls, intrusion detection systems, and other network security devices that protect the servers from attacks originating from the Internet. The cloud brings specific issues:

\begin{itemize}
    \item \emph{confidentiality and integrity of data in transit}: Amazon, for instance, had security bugs with the digital signature on SimpleDB, EC2, and SQS accesses in 2008;
    \item \emph{little or no system logging and monitoring}: only the cloud provider has this capability, so attacks are difficult to trace;
    \item \emph{reassigned IP addresses}: services can be exposed unexpectedly, and spammers using EC2 are difficult to identify;
    \item \emph{availability of cloud resources}: some factors, such as DNS, are controlled by the cloud provider;
    \item \emph{physically separated tiers become logically separated}, for example in three-tier web applications.
\end{itemize}

\textbf{Host level.} Security at the host level concerns the individual servers making up the infrastructure (operating system, applications, and stored data), and protects them from attacks originating from within the infrastructure. Two elements are specific to the cloud. The \emph{hypervisor} manages the virtual machines running on the physical servers, so a compromise of the hypervisor, for example through a zero-day vulnerability, can lead to a compromise of all the VMs running on it; its security is improved by using secure hypervisors, keeping them up to date, and using strong access controls. The \emph{virtual machines} run the applications of the cloud services, and their security is improved in the same way, with secure VM images, updates, and strong access control. The main weak points are SSH private keys (if their file mode is not appropriately set), VM images (especially private VMs), and vulnerable services.

\begin{warningblock}[Risks of VMs and containers]
    Virtualization and containerization simplify the implementation of resource management policies, improve intrusion prevention and detection, allow secure logging and intrusion protection, and make software testing more efficient and flexible. They also introduce risks: the number of VMs can explode; snapshots allow rolling back to a state that can be exploited; and shared images may contain backdoors and leftover credentials, unsolicited connections, or malware. It was found that 22\% of the scanned Linux AMIs contained credentials allowing an intruder to log into the system remotely.
\end{warningblock}

The operating system implements minimal security on access control, authentication usage, and cryptographic usage policies, which are all elements of mandatory OS security. Applications with special privileges that perform security-related functions are called \textbf{trusted applications}, and should be allowed only the lowest level of privileges required to perform their functions. An OS isolates applications from one another poorly: once an application is compromised, the entire physical platform and all the applications running on it can be affected. This is the weakness that the isolation of \cref{sec:linux_namespaces} and \cref{sec:linux_cgroups} mitigates, though not completely (\cref{tab:vm-vs-container}).

\textbf{Application level.} Security at the application level, the highest, concerns the applications running on the cloud servers: the code that makes up the application, the data it processes, and the users who access it. It protects the servers from attacks that exploit vulnerabilities in the application code.

\subsection{Data Security}

For data, the first step is to identify the security boundary between the responsibilities of client and vendor, and to determine the sensitivity of the data to risk. Data should be transferred and stored in an encrypted format, and clients should be separated from direct access to the shared cloud storage. Four mechanisms are used to protect data.

\begin{itemize}
    \item \textbf{Access control} determines who can access what data and under which conditions, and is typically implemented by combining authentication, authorization, and auditing.
    \item \textbf{Auditing} monitors and records access to data, typically through logging, monitoring, and reporting.
    \item \textbf{Authentication} verifies the identity of a user, typically through passwords, biometrics, and other mechanisms.
    \item \textbf{Authorization} determines what data a user can access, typically through access control lists, role-based access control, and other mechanisms.
\end{itemize}

Data must be isolated from direct client access, by creating a layered access to it, and segregated on the basis of tenants. \cref{fig:data-security} shows such a layered access. The client sends a data request over the Internet to a proxy, which applies the rules and restates the request; a broker sends the modified request to the cloud storage; the storage replies to the broker, which relays the data to the proxy, and the proxy finally returns the response to the client. The client never talks to the storage directly.

    \centering
    % \includegraphics[width=0.55\textwidth]{assets/fig51.png} % TODO: check filename against ch7_old.tex
    \caption{Data segregation and isolation through a proxy and a broker.}
    \label{fig:data-security}
\end{figure}

\vspace{-1em}

Most cloud service providers store data in an encrypted form, on the server side or on the client side (for example Amazon S3 uses the 256-bit Advanced Encryption Standard). The AWS documentation provides Java examples of client-side encryption (\href{https://docs.aws.amazon.com/AmazonS3/latest/dev/UsingClientSideEncryption.html}{UsingClientSideEncryption}). Encryption is not a complete answer, however.

\begin{warningblock}[Keep your keys]
    A problem with encrypted data may result in data that cannot be recovered, and encryption does nothing to prevent data loss. Whoever holds the data must therefore keep the encryption keys safe.
\end{warningblock}
