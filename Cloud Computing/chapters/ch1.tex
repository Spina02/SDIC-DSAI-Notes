\chapter{Introduction} \label{ch:cloud_intro}

\section{What is Computing?}

\begin{definitionblock}[Computing]
\bfit{Computing} is the process of using computer technology to complete a given, goal-oriented task; it may encompass the design and development of both software and hardware systems for a broad range of purposes.
\end{definitionblock}

Today, every scientific instrument, from single detectors to continent-scale telescope arrays, relies on computing for sensor control, data processing, collaboration, and data access. Computational modelling and data analytics now span nearly all scientific and engineering fields, with much research focused on capturing and analysing the vast data streams generated by modern instruments. This chapter outlines how the supporting computing infrastructure has evolved: from centralized machines, through distributed, cluster, and grid computing, to the utility-based cloud computing at the heart of this course.

\section{Distributed Computing} \label{sec:distributed_computing}

\vspace{-0.7em}

\begin{minipage}{0.5\textwidth}
As problems outgrew what a single computer could handle, computing moved from a single machine to a "network" of collaborating systems, and from there progressively through clustered, grid-based, and utility models toward the cloud computing paradigm examined throughout the rest of this course.
\end{minipage}%
\hfill
\begin{minipage}{0.47\textwidth}
    \vspace{-2em}
    \centering
    \includegraphics[width=0.95\textwidth]{assets/fig1.png}
    \captionof{figure}{The evolution of computing, from a centralized mainframe to the cloud.}
    \label{fig:computing-evolution}
\end{minipage}

\begin{definitionblock}[Distributed System]
A \bfit{distributed system} is a collection of autonomous computers that are interconnected with each other and cooperate, thereby sharing resources such as printers and databases.
\end{definitionblock}

The network serves as the glue that connects otherwise independent resources. Applications adopt this model for several reasons: some problems are inherently distributed and best represented as sets of interacting components; others are compute-intensive but need little communication, as in \textbf{High Throughput Computing} (Section~\ref{sec:cluster_hpc}); and some are data-intensive, involving data volumes or sizes too great for one machine. Distributed computing also enables \textbf{cycle scavenging}: by harnessing idle desktop machines, as in systems like Condor, spare capacity supports other users and jobs. Beyond increasing capacity, distribution brings structural benefits. \textbf{Fault tolerance} arises because each node handles only part of the work: if one fails, the rest can keep running, as long as failure is detected and work reassigned. \textbf{Resource sharing} lets users and sites pool capacity; \textbf{load balancing} spreads work so no node becomes a bottleneck. Distributed systems also \textbf{scale} easily by adding nodes, growing aggregate performance.

\subsection{Distributed System Architectures}

The way processes running on different machines interconnect and communicate defines the system's architecture.

\begin{itemize}
    \item \textbf{Client-server}: Resource management and control are centralized at one or more servers, which provide services and manage resources in response to requests from multiple, independent client machines. This is a foundational model for web, database, and enterprise applications.
    \item \textbf{Three-tier architecture}: The application's logic is separated into three distinct layers: the client (presentation), an intermediate application or business logic layer, and a backend data storage layer. This structure simplifies clients, enhances security, and improves scalability by decoupling user interfaces from the core application and data.
    \item \textbf{Peer-to-peer}: Responsibilities and resources are distributed uniformly among all participating machines, called peers. Each peer simultaneously acts as both client and server, exchanging data and services with others. This decentralized approach underlies technologies such as file-sharing networks and blockchain systems, providing resilience and scalability.
\end{itemize}

\subsection{Case Study: Apache Hadoop and MapReduce}

\begin{minipage}{0.5\textwidth}
\textbf{Apache Hadoop} provides a distributed, scalable platform for data analytics built on two main components. The \textbf{Hadoop Distributed File System} (HDFS) stores and replicates large files across many machines for resilience. 

\smallskip

On top of HDFS, \textbf{MapReduce} offers a high-level parallel programming model with two phases: the \textit{map} phase applies a function independently to each input, outputting key-value pairs; these are then \textit{shuffled} so that all pairs with the same key are grouped on the same node; finally, the \textit{reduce} phase combines values for each key into results.
\end{minipage}%
\hfill
\begin{minipage}{0.45\textwidth}
    \centering
    \includegraphics[width=\textwidth]{assets/map_reduce.png}
    \captionof{figure}{MapReduce workflow.}
    \label{fig:map-reduce}
\end{minipage}

\medskip

A central \textbf{job tracker} on the namenode schedules map and reduce tasks across data nodes running \textbf{task trackers}, which send regular heartbeat updates; failed tasks are rescheduled automatically. The Hadoop ecosystem supports extensions for streaming data (Storm, Flume), graph analytics (Giraph), relational data (Sqoop), and machine learning (Mahout).

\section{Cluster Computing} \label{sec:cluster_hpc}

\begin{definitionblock}[Cluster]
A \bfit{cluster} is a group of linked computers working together closely enough that, in many respects, they form a single machine. Its components are commonly, though not always, connected through a fast local area network.
\end{definitionblock}

Clusters are deployed to improve performance and/or availability beyond what a single computer could provide, while remaining considerably more cost-effective than a single machine of comparable speed. Three broad classes are commonly distinguished:

\begin{itemize}
    \item \textbf{High-availability clusters} provide redundancy to eliminate single points of failure, ensuring services remain running even if nodes fail.
    \item \textbf{Network load-balancing clusters} distribute an incoming workload evenly across multiple, often redundant, back-end nodes that all process requests concurrently, as in web or mail server farms.
    \item \textbf{HPC clusters} feature a low-latency interconnect, message-passing libraries, a parallel filesystem, and dedicated HPC system software, and are the workhorses of large-scale simulations.
\end{itemize}

\medskip

\begin{minipage}{0.63\textwidth}
In practice, users interact with a cluster through a login node, from which jobs are submitted to a scheduler as shell scripts running within a defined application environment; this batch model is not well suited to interactive work, and each job is queued with a limited computing time allocation. The filesystem is typically organized into a home area, a scratch area for temporary data, and a data area, all backed by a shared parallel filesystem visible to every compute node. 
\end{minipage}%
\hfill
\begin{minipage}{0.32\textwidth}
    \centering
    \includegraphics[width=0.97\textwidth]{assets/fig5.png}

    \vspace{-0.5em}

    \captionof{figure}{A computer cluster.}
    \label{fig:cluster}
\end{minipage}

\medskip

Compared to a single supercomputer of equivalent aggregate power, a cluster is cheaper, more resilient (the failure of one or a few nodes does not bring the whole system down), naturally suited to a multi-user, shared environment, and easy to expand, partition, or shrink as requirements evolve. The \href{https://www.top500.org}{TOP500} list ranks the world's most powerful HPC clusters, most of which today combine conventional CPUs with GPU accelerators.

\subsection{High-Performance versus High-Throughput Computing}

There are two broad classes of computing:

\begin{itemize}
    \item \textbf{High Performance Computing} (HPC, or \textit{capability} computing): focuses on large, tightly coupled jobs running on many nodes, making heavy use of the interconnect.
    \item \textbf{High Throughput Computing} (HTC, or \textit{capacity} computing): focuses on many independent, mostly single-node jobs that require little or no interconnect.
\end{itemize}

\begin{figure}[H]
    \centering
    \includegraphics[width=0.7\textwidth]{assets/hpc-vs-htc.png}
    % \caption{The difference between HPC and HTC.}
    \label{fig:hpc-htc}
\end{figure}

Designing an HTC application involves breaking a problem into independent parts, processing as many as possible in parallel, then combining their results for the final answer.

\begin{exampleblock}[The LOFAR pipeline (HTC)]
The International LOFAR Telescope is a distributed radio interferometer with stations across Europe, sampling the sky in many independent frequency sub-bands. Each observation (typically 8 hours, 115-175\,MHz, 371 sub-bands) and full surveys containing hundreds of such observations, can each be processed largely independently, making LOFAR data reduction well suited to HTC. On a single node, calibrating one observation takes about 2-3 hours for the calibrator and 12-24 hours for the target field, yielding around 100\,GB of data. Ideally, dividing the work across $\sim$100 sub-bands would cut the total time by a similar factor; in practice, however, single-node tests showed this optimistic, posing the usual HTC question: where is the real bottleneck, I/O, network, or elsewhere?
\end{exampleblock}

Beyond partitioning, using an HPC cluster effectively raises three further challenges. 
\begin{itemize}
    \item The \textbf{computing challenge} is to exploit both multi-core CPUs and many-core accelerators (GPUs) to improve a code's performance.
    \item The \textbf{memory challenge} arises because huge datasets cannot be loaded into, or handled by, the memory of a single machine; distributed-memory systems, coordinated through the \textbf{MPI} standard, provide a feasible solution.
    \item The \textbf{data challenge} concerns the management, archiving, and access of the raw data, the intermediate science products, and the final outcomes of the analysis.
\end{itemize}

\subsection{Case Study: The N-body Problem}

The \bfit{N-body problem} asks for the future trajectories of a group of objects interacting under their mutual gravitational forces, given each object's current position and velocity; in astronomy it is studied at scales ranging from asteroid dynamics near Jupiter (Bro\v{z} et al.\ 2008) to the largest gravitationally bound structures in the Universe (Angulo et al.\ 2012). 

\begin{minipage}{0.5\textwidth}
Direct summation evaluates every pairwise interaction and therefore costs $O(N^2)$ operations per timestep. The \textbf{Barnes-Hut algorithm} reduces this to $O(N\log N)$ by recursively subdividing space into a hierarchical tree, an octree in three dimensions: particles lying in a distant branch of the tree are treated collectively, their combined pull approximated by a single mass placed at their common centre of mass, so that only nearby particles require an exact, direct force calculation.
\end{minipage}%
\hfill
\begin{minipage}{0.47\textwidth}
    \centering
    \includegraphics[width=\textwidth]{assets/fig6.png}
    \captionof{figure}{Barnes-Hut tree reduces $N$-body force computations.}
    \label{fig:nbody}
\end{minipage}

A typical parallel implementation using MPI involves the following communication pattern:
\begin{enumerate}
    \item Build the octree, typically on a primary MPI rank, and broadcast it to every other rank.
    \item Distribute particle positions and velocities across the ranks; each rank traverses the shared octree to compute the total force on its own particles.
    \item Update velocities and positions using a time-integration scheme, often offloaded to a GPU.
    \item Gather the updated particle catalogue back to the primary rank, and repeat for the next timestep.
\end{enumerate}
Because every rank must exchange information at every single timestep, this algorithm is \textbf{tightly coupled}, in sharp contrast to the loosely coupled, independent chunks of an HTC workload such as LOFAR's frequency sub-bands.

\begin{observationblock}[Sizing the data]
A single simulation or survey can produce far more data than a workstation can store: pipelines may start with 200\,TB, process $\sim$2\,TB, and generate 20\,TB of results. Future projects, like the Square Kilometre Array, expect 700\,PB yearly: beyond any single data centre. Such scale drives the move toward grid, utility, cloud, and edge computing.
\end{observationblock}

\section{Grid Computing} \label{sec:grid_computing}

\begin{definitionblock}[Grid]
A \bfit{grid} is a framework for flexible, secure, coordinated resource sharing among dynamic collections of individuals, institutions, and resources: a collection of geographically separated clusters, connected by a network and unified by a software layer, the \bfit{middleware}, that turns them into a single, coherent virtual machine, in which the workstation across the continent is no less accessible than the one down the hall.
\end{definitionblock}

\medskip

\begin{center}
    \centering
    \begin{minipage}{0.7\textwidth}
        \includegraphics[width=\textwidth]{assets/fig7.png}
    \end{minipage}%
    \hfill
    \begin{minipage}{0.27\textwidth}
        \captionof{figure}{A grid unifies geographically distributed resources, via a layer of middleware, into a single virtual system.}
        \label{fig:grid}
    \end{minipage}
\end{center}

\medskip

Grids exist because the size or complexity of a problem often requires people from several organisations to collaborate and share computing resources, data, and instruments; the resulting collaboration is known as a \textbf{virtual organization}. Grid middleware, such as the Globus Toolkit (from the Globus Alliance), gLite (developed for EGEE), Unicore, GridBus, or GRIA, is precisely the software layer sitting between the operating system and the applications that makes this sharing possible.

\medskip

\begin{minipage}{0.52\textwidth}
Concretely, it layers a \textit{fabric} of raw resources (the OS, HPC systems, and local schedulers such as PBS, LSF, or Condor), \textit{low-level services} for security, job execution, and file transfer, \textit{high-level} (collective) services for cross-site scheduling, data management, and information systems, and finally the \textit{application layer} itself. The Worldwide LHC Computing Grid is a landmark example: LHC data is distributed across a tiered architecture and processed using gLite-based middleware.
\end{minipage}%
\hfill
\begin{minipage}{0.45\textwidth}
    \vspace{-0.5em}

    \includegraphics[width=\textwidth]{assets/grid-layers.jpg}

    \vspace{-0.5em}

    \captionof{figure}{Grid computing hierarchy.}
\end{minipage}

\medskip

For all its power, the grid model has practical limitations. It is a rigid, largely homogeneous environment in which every participating resource must be installed, maintained, and monitored consistently. It suits HTC-style workloads well, but at the cost of a substantial complexity to use efficiently; software licensing across different administrative domains is often problematic; the middleware in use imposes its own implementation limits; and sharing resources across independent institutions inevitably raises political, as well as technical, challenges.

\section{Utility, Cloud, and Edge Computing} \label{sec:utility_cloud_edge}

\subsection{Utility Computing}

\begin{definitionblock}[Utility Computing]
\bfit{Utility computing} is a service-provisioning model in which a provider makes computing resources and infrastructure available to customers and charges them for their actual, on-demand usage rather than a flat rate, so that a resource is rented rather than owned.
\end{definitionblock}

It is, in essence, a theoretical concept that cloud computing later realised in practice. Its defining features are a pay-per-use pricing model, though flat-rate or metered variants (the pricing model is really what distinguishes utility computing from other paradigms), optimised resource utilisation, the outsourcing of infrastructure management to the provider, an appearance of "infinite" resource availability, shared access to applications and libraries, and a high degree of automation. In return, the customer must trust the provider on several fronts: data backup and security, the provider's own competence, a clearly defined \textbf{Service Level Agreement} (SLA) specifying the guaranteed quality of service, and a chargeback model from which real value can actually be extracted.

\subsection{Cloud Computing}
 
Cloud computing brings together previous trends: grid computing's distributed resource sharing, utility computing's pay-per-use model, and \textbf{Software as a Service} (SaaS), converging into a single paradigm for delivering computing over the Internet.
 
\begin{definitionblock}[Cloud Computing]
\bfit{Cloud computing} is a model for delivering on-demand, self-service access to a shared pool of configurable computing resources, such as networks, servers, storage, and applications, that can be rapidly provisioned and released with minimal management effort, typically over the Internet and billed according to actual usage.
\end{definitionblock}

\subsection{Edge Computing}

\begin{minipage}{0.48\textwidth}
The cost of moving data, in terms of both latency and energy, increases dramatically with distance, as illustrated in Figure~\ref{fig:edge}. On-chip and register operations require only a few picojoules per operation, whereas moving data off-chip (between cores, nodes, or across systems) incurs one to several orders of magnitude greater energy consumption. For example, intra-node communication (such as within a single SMP server) is significantly more expensive than on-chip or intra-core transfers, and inter-node communication (e.g., via MPI across a distributed system) is more costly still.
\end{minipage}%
\hfill
\begin{minipage}{0.49\textwidth}
    \centering
    \includegraphics[width=\textwidth]{assets/data-moving.png}
    \captionof{figure}{The energy cost of moving data increases with distance.}
    \label{fig:edge}
\end{minipage}

\medskip

This scaling effect means that the farther data must travel, the more prohibitive its movement becomes, making it often more efficient (in both power and performance) to move computation closer to where the data resides rather than vice versa.

\begin{definitionblock}[Edge Computing]
\bfit{Edge computing} is a distributed computing paradigm in which processing and computation are performed mainly on device nodes close to the source of the data, known as \textbf{edge devices} (sensors, mobile terminals, or the instruments themselves), rather than in a centralized cloud environment or data centre.
\end{definitionblock}

\smallskip
 
\begin{minipage}{0.35\textwidth}
A network of small "micro data centres" embedded near the instruments stores or processes the most time-critical data locally, forwarding only the necessary results to a centralized repository or cloud storage system; this reduces both the traffic reaching the central archive and, as the observation above suggests, the energy and latency cost of the whole pipeline.
\end{minipage}%
