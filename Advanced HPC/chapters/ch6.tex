\chapter{GPUs and Accelerated Computing}

\section{Introduction to Accelerated Computing}

The constant demand for computational power in science and engineering has driven the evolution of computer architecture. For decades, performance gains were fueled by increasing clock frequencies and instruction-level parallelism, but physical limitations have shifted the focus toward massive parallelism. This paradigm shift requires a corresponding evolution in programming models to effectively harness the capabilities of modern hardware.

This chapter introduces \textit{accelerated computing}, a paradigm where a specialized, highly parallel processing unit, the Graphics Processing Unit (GPU), is used in conjunction with a traditional Central Processing Unit (CPU) to accelerate computationally intensive portions of an application. We will explore the architectural differences between CPUs and GPUs, delve into the CUDA C/C++ programming model for NVIDIA GPUs, and discuss fundamental concepts such as memory hierarchies, thread organization, and performance optimization.

\subsubsection{Key Performance Metrics}

When evaluating system performance, three metrics are crucial:
\begin{itemize}
    \item \textbf{Latency}: The time it takes to perform a single operation or access a single piece of data (e.g., time to fetch a value from memory). Measured in seconds.
    \item \textbf{Bandwidth}: The rate at which data can be transferred. Measured in bytes per second.
    \item \textbf{Throughput}: The total number of operations completed in a given amount of time. Measured Floating-Point Operations Per Second (FLOPS).
\end{itemize}

CPUs are optimized for low latency, while GPUs are designed for high throughput and high memory bandwidth, sacrificing single-thread latency to achieve massive parallelism.

\begin{warningblock}[Architecture and Programming Models]
    A fundamental principle in HPC is that changes in hardware architecture necessitate changes in programming models to achieve efficiency. Code written for a latency-oriented CPU will not perform well on a throughput-oriented GPU.
\end{warningblock}

\subsection{Architectural Design Philosophies: Latency vs. Throughput}

CPUs and GPUs are designed with fundamentally different goals, their architectures reflect this.


\begin{minipage}{0.65\textwidth}
\subsubsection{Latency-Oriented Design (CPUs)}

A CPU is a \textbf{latency-oriented} device, designed to execute a single thread of instructions as quickly as possible:
\begin{itemize}
    \item \textbf{Powerful Cores}: A CPU has a small number of powerful, general-purpose cores capable of complex control flow and integer/floating-point arithmetic.
    \item \textbf{Large Caches}: It employs a deep, multi-level cache hierarchy (L1, L2, L3) to minimize memory latency. The goal is to keep data as close to the core as possible, to reduce waiting time for data from main memory.
    \item \textbf{Sophisticated Control Logic}: Features as branch prediction, speculative execution are used to maximize performance.
\end{itemize}
\end{minipage}%

\subsubsection{Virtual Memory: The Great Abstraction}

\begin{minipage}{0.65\textwidth}
\textbf{Virtual memory} is a foundational abstraction in all modern CPUs, allowing each process to believe it has access to a private, contiguous range of addresses, providing several advantages:

\begin{itemize}
    \item \textbf{Simplified Programming Model}: Programs can use memory addresses freely.
    \item \textbf{Isolation}: Each process is protected from accidental or malicious access to others' memory.
    \item \textbf{Efficient Resource Utilization}: The OS can move data between physical memory and storage transparently.
\end{itemize}

\medskip

The virtual address used by a program is translated into a physical address by the CPU hardware (the Memory Management Unit, MMU) using page tables maintained by the operating system.
\end{minipage}%
\hfill
\begin{minipage}{0.33\textwidth}
    \vspace{-1em}

    \caption{Translation of virtual to physical addresses.}
\end{figure}
\end{minipage}

\begin{warningblock}{Page Faults and Swapping}
    If a program accesses memory that is not currently mapped to physical RAM, a \textbf{page fault} occurs. The OS may need to load the required page from disk (swap space), causing a major slowdown.
\end{warningblock}

When a CPU needs data, it first checks the fastest cache (L1), then proceeds to L2, L3, and finally DRAM if necessary. The principle of \textbf{locality} (recently or nearby accessed data being more likely to be reused) underpins cache design.


Caching increases effective memory bandwidth and reduces average memory access latency---key for maximizing CPU (and to a certain extent, GPU) performance.

\subsubsection{From single core to multicore}

The end of frequency scaling pushed CPU vendors towards \textbf{multicore} designs, where several physical cores share the package and (typically) the last-level cache. Each core retains the latency-oriented features described above; what changes is that the chip now exposes \emph{thread-level} parallelism in addition to instruction-level parallelism.

A few consequences are worth keeping in mind when reasoning about CPU-side performance:
\begin{itemize}
    \item \textbf{Shared last-level cache}. L1 and (usually) L2 are private per core, while the L3 is shared. Threads cooperating on the same data benefit from the shared cache, but threads with disjoint working sets compete for capacity.
    \item \textbf{Cache coherence}. Hardware protocols (e.g.\ MESI) keep private caches consistent across cores, so a write by one core is eventually visible to the others. Coherence has a cost: ping-ponging a cache line between cores (\textit{false sharing}) is one of the most common performance pitfalls in multithreaded code.
    \item \textbf{SMT / hyperthreading}. Each physical core often exposes two logical threads that share the execution resources. SMT helps hide short stalls but does \emph{not} double throughput.
    \item \textbf{NUMA}. On multi-socket nodes, memory is partitioned across sockets and access to a remote socket is slower than to the local one. We discussed first-touch placement and pinning in chapter~3; the same considerations apply whenever a CPU thread feeds work to a GPU.
\end{itemize}

This is the architectural baseline against which a GPU is compared in the next subsection: many simple cores in place of a few sophisticated ones, no per-thread cache, and a programming model that explicitly partitions work across thousands of execution contexts rather than relying on the hardware to extract parallelism from a serial instruction stream.

\subsubsection{Throughput-Oriented Design (GPUs)}
A GPU, in contrast, is a \textbf{throughput-oriented} device, designed to execute thousands of parallel threads simultaneously. Its architecture is specialized for data-parallel tasks:
\begin{itemize}
    \item \textbf{Many Simple Cores}: A GPU contains thousands of simpler, more energy-efficient cores grouped into \textit{Streaming Multiprocessors} (SMs).
    \item \textbf{Smaller Caches, High-Bandwidth Memory}: While GPUs have caches, they are smaller relative to the number of cores. The design prioritizes high memory bandwidth to feed the massive number of cores with data concurrently. The philosophy is to "hide" latency by having other work to do. While one group of threads waits for data, the SM switches to another group that is ready to execute.
    \item \textbf{Simple Control Logic}: GPUs use simpler control logic and are optimized for executing the same instruction on multiple data elements (a model known as SIMT, or Single Instruction, Multiple Threads).
\end{itemize}
This design is ideal for workloads where the same computation can be performed independently on many different data points, such as matrix multiplication, image processing, and scientific simulations.

\section{The GPU Architecture}

In a typical accelerated node, the CPU is referred to as the \textbf{host} and the GPU as the \textbf{device}. They are physically distinct processors with their own memory spaces, connected by a high-speed interconnect like the PCIe bus. A key task in accelerated computing is managing the transfer of data and control between the host and device.

GPUs are designed to execute a massive number of threads simultaneously. In the CUDA model, threads are launched in groups of 32, known as \textbf{warps}. All threads in a warp execute the same instruction at the same time, making them the fundamental unit of scheduling on the GPU. This execution model is highly efficient for data-parallel problems but requires careful programming to avoid performance pitfalls.

\subsection{NVIDIA Ampere Architecture}

The NVIDIA A100 GPU, used in the Leonardo supercomputer, is based on the \textbf{Ampere architecture}. A full Ampere GPU consists of several \textbf{Graphics Processing Clusters (GPCs)}, which are further subdivided into \textbf{Streaming Multiprocessors (SMs)}. The SM is the core processing unit of the GPU.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.8\textwidth]{assets/nvidia-ampere.png}
    \caption{High-level overview of the NVIDIA Ampere A100 GPU architecture, showing the arrangement of GPCs and SMs.}
    \label{fig:nvidia-ampere}
\end{figure}

\begin{minipage}{0.6\textwidth}
The \textbf{Streaming Multiprocessor (SM)} is the heart of the NVIDIA GPU. In the Ampere architecture, each SM is partitioned into four processing blocks, each with its own instruction buffer, warp scheduler, and dispatch units. This allows the SM to manage and execute multiple warps concurrently.

Key components within an Ampere SM include:
\begin{itemize}
    \item \textbf{FP32/FP64 Cores}: CUDA cores dedicated to single- and double-precision floating-point arithmetic.
    \item \textbf{Tensor Cores (3rd Gen)}: Specialized units that accelerate mixed-precision matrix multiply-accumulate operations, crucial for AI and deep learning workloads. They support new data formats like TF32 and BFloat16.
    \item \textbf{Shared Memory and L1 Cache}: A configurable block of high-speed on-chip memory that can be used as a software-managed cache (\texttt{L1}) or a scratchpad for thread cooperation (\texttt{shared memory}).
    \item \textbf{Warp Schedulers}: Hardware units that select which warps are ready to execute their next instruction.
\end{itemize}
The SM is designed to keep its execution units busy by rapidly context-switching between different warps. If one warp stalls (e.g., waiting for data from global memory), the scheduler immediately switches to another resident warp that is ready to execute, thereby hiding memory latency and maximizing computational throughput.
\end{minipage}%

\section{CUDA Programming Model}

CUDA is NVIDIA's C/C++ extension for programming the device. The model rests on three pillars: \emph{function qualifiers} that say where a function lives, the \emph{kernel-launch syntax} that schedules a function on the GPU, and the runtime API for moving data between host and device. We start with the syntax and then look at how errors are reported, since CUDA's asynchronous execution makes error handling non-trivial.

\subsection{Function qualifiers and kernel launches}

A function annotated with one of CUDA's qualifiers is compiled for the corresponding side of the device boundary:
\begin{itemize}
    \item \plaintt{\_\_global\_\_} --- the function is a \textbf{kernel}: callable from the host (and, on recent GPUs, from the device), executed on the device. It must return \plaintt{void}.
    \item \plaintt{\_\_device\_\_} --- callable from device code only, executed on the device. Used for helper routines that run inside a kernel.
    \item \plaintt{\_\_host\_\_} --- ordinary host function. Implicit when no qualifier is given.
    \item \plaintt{\_\_host\_\_ \_\_device\_\_} --- compiled for both sides; useful for utilities that need to be reused on host and device.
\end{itemize}

A kernel is launched with the \texttt{<<<\,grid,\,block\,>>>} \textit{execution-configuration} syntax, which fixes how many thread blocks and how many threads per block the GPU will instantiate:

\begin{codeblock}[language=C]
__global__ void GPUFunction() {
    printf("Hello from GPU!\n");
}

int main() {
    CPUFunction();
    GPUFunction<<<1, 1>>>();    // 1 block, 1 thread
    cudaDeviceSynchronize();    // wait for the GPU to finish
}
\end{codeblock}

A CUDA kernel runs as a \textit{grid} of threads, all executing the same code. Each thread sees a unique identifier through \texttt{threadIdx}, \texttt{blockIdx} and \texttt{blockDim}; we use it in the next section to map threads to data elements.

\subsection{SIMT vs SIMD}

In cuda programming, we use the SIMT (Single Instruction Multiple Thread) model.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.45\textwidth]{assets/simt.png}
    \caption{SIMT vs SIMD}
    \label{fig:simt-simd}
\end{figure}

\begin{itemize}
    \item \textbf{SIMD}: “One instruction, one data chunk.”
    \begin{itemize}
        \item A single instruction operates on multiple data elements simultaneously
        \item Requires wide vector units in hardware (e.g., 4 or 8 lanes)
        \item A SIMD register (or a vector register) can hold many values (2 - 16 values or more) of a single type
        \item Operates on packed data in wide registers (e.g., 128-bit or 256-bit)
        \item All elements in the vector must follow the same control flow—no divergence
        \item Vectorisation helps you write code which has good access patterns to maximise bandwidth
    \end{itemize}
    \item \textbf{SIMT} "Single Instruction, Multiple Threads".
    \begin{itemize}
        \item Uses scalar execution units, not wide vectors, rigid, lockstep vector processing
        \item 32 threads in a warp share a single instruction fetch, executed over multiple cycles (e.g., 4 cycles
        on 8 CUDA cores)
        \item Flexible, thread-level parallelism with divergence support.
        \item Single instruction, multiple flow paths
        if statements are allowed!
    \end{itemize}
\end{itemize}

SIMT allows CUDA GPU to perform “vector” computations on scalar cores. Much easier to vectorise than getting compiler to autovectorize on CPU.

\subsection{Compilation with nvcc}

CUDA source files (\plaintt{.cu}) mix host and device code. The NVIDIA compiler driver \plaintt{nvcc} separates them: device-side code is compiled to PTX (a virtual ISA) and then to a target-specific binary, while host-side code is delegated to the system compiler (\plaintt{gcc}/\plaintt{clang}). A typical invocation on Leonardo is

\begin{codeblock}[language=bash]
nvcc -arch=sm_80 -O3 -o vecadd vecadd.cu
\end{codeblock}

\begin{itemize}
    \item \plaintt{-arch=sm\_80} selects the target compute capability (Ampere = 8.0). Without this flag \plaintt{nvcc} compiles for an older default and you may miss hardware features.
    \item \plaintt{-O3} enables host-side optimisation (device-side optimisation is on by default).
    \item \plaintt{-run} (used in many of the course examples) compiles \emph{and} runs the resulting binary, which is convenient for one-off experiments.
\end{itemize}

\subsection{Error handling and the asynchronous error model}

Every CUDA Runtime API call returns a value of type \plaintt{cudaError\_t}; \plaintt{cudaSuccess} means everything went well, anything else is an error code that \plaintt{cudaGetErrorString()} translates into a human-readable string. The synchronous case is straightforward:

\begin{codeblock}[language=C]
cudaError_t err = cudaMallocManaged(&a, size);
if (err != cudaSuccess)
    fprintf(stderr, "alloc error: %s\n", cudaGetErrorString(err));
\end{codeblock}

Kernel launches are different: they are \textbf{asynchronous}. The \texttt{<<<...>>>} call enqueues the kernel and returns immediately, even if the kernel cannot start (e.g.\ because the launch configuration is invalid) or fails later (e.g.\ a segmentation fault on the device). For that reason CUDA exposes \emph{two} layers of error reporting around a launch:

\begin{codeblock}[language=C]
myKernel<<<blocks, threads>>>(args);

// 1) launch-time errors (bad configuration, too much shared memory, ...)
cudaError_t launchErr = cudaGetLastError();
if (launchErr != cudaSuccess) { /* handle */ }

// 2) execution-time errors (only visible at the next sync point)
cudaError_t runErr = cudaDeviceSynchronize();
if (runErr != cudaSuccess) { /* handle */ }
\end{codeblock}

\plaintt{cudaGetLastError()} clears the sticky error flag, so calling it once after each launch is the safe pattern. Run-time faults inside a kernel only surface at the next synchronisation, which is why projects routinely wrap launches in a \texttt{CHECK\_CUDA} macro that calls both functions.

\begin{tipsblock}[Debugging tip]
Setting the environment variable \plaintt{CUDA\_LAUNCH\_BLOCKING=1} forces every kernel launch to be synchronous, so a crash points exactly at the offending kernel instead of at a far-away \plaintt{cudaDeviceSynchronize()}. Do this for debugging only --- it serialises all kernels and destroys the latency-hiding the GPU relies on.
\end{tipsblock}

\section{GPU Thread Hierarchy}

A gpu consists of thousands of grids, each one containing thousands of thread blocks (teams), each one containing 1024 threads divided into warps of 32 threads each.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.8\textwidth]{assets/gpu-hierarchy.png}
    \caption{GPU Thread Hierarchy}
    \label{fig:gpu-thread-hierarchy}
\end{figure}

All thread blocks in a grid must have the same number of threads, ensuring homogeneity across the GPU workload. To process $N$ elements in parallel, we need to launch at least $N$ concurrent threads on the device. Threads within the same block (or team) can efficiently cooperate by exchanging data through a shared memory cache. Importantly, each block is executed independently, and there is no guarantee on the order in which blocks are scheduled or executed by the GPU.

CPUs and GPUs have physically distinct memory regions connected by the PCIe bus.

Every time we want to compute something on a GPU we need to perform some steps:

\begin{itemize}
    \item Allocate GPU memory
    \item Copy data from the host to the GPU
    \item Load GPU program and execute, caching data on chip for performance
    \item Copy results from the GPU memory to the host memory
    \item Free the GPU memory
\end{itemize}

We can see how the code for cpu is very similar to the one for gpu, but with the addition of the cuda functions.

\begin{minipage}{0.48\textwidth}
\textbf{CPU code}

\begin{codeblock}[language=C]
int N = 10000;
size_t size = N * sizeof(int);

int *a;
a = (int *) malloc(size);

free(a);
\end{codeblock}
\end{minipage}%
\hfill
\begin{minipage}{0.48\textwidth}
\textbf{GPU code}

\begin{codeblock}[language=C]
int N = 10000;
size_t size = N * sizeof(int);

int *a;
cudaMallocManaged(&a, size);

cudaFree(a);
\end{codeblock}
\end{minipage}

\subsubsection{Choosing the optimal grid size}

Let's start by choosing the \bfit{optimal block size}. To do that, we need to write an execution configuration that creates more threads than necessary, then pass a value as an argument into the kernel (N) that represents that total size if the data set to be processed/total threads needed to complete the work.

Then, we need to calculate the global index and if it does not exceed N perform the kernel work.

\begin{codeblock}[language=C]
__global__ vectorSum(int N) {
    int idx = threadIdx.x + blockIdx.x * blockDim.x;
    if (idx < N) { // only do work if it does}
}
\end{codeblock}

Maximum size at each level of the thread hierarchy is device dependent.

On A100 typicaly you get:

\begin{itemize}
    \item Maximum number of threads per block: 1024
    \item Maximum sizes of x-, y-, and -z dimensions of threads block: 1024 x 1024 x 64
    \item Maximum sizes of each dimension of grid of thread blocks: 65535 x 65535 x 65535 (about 280,000 billion blocks)
\end{itemize}

The best performance is achieved for blocks that contain a number of threads that is a multiple of 32, due to GPU hardware traits.

\begin{exampleblock}[Choosing the optimal block size]
We want to run 1000 parallel task with blocks containing 256 threads. How do we choose the optimal block size?

\begin{codeblock}[language=C]
int N = 100000; size_t threads_per_blocks = 256;
size_t number_of_blocks = (N + threads_per_block - 1) / threads_per_block;
kernel<<<number_of_blocks, threads_per_block>>>(N);
\end{codeblock}

The "-1" term is added to round up the division if necessary.
\end{exampleblock}

A limited number of threads (1024) can fit inside a thread block, so to increase parallelism we coordinate work across many blocks. Each thread computes its global index and works on the corresponding data element:

\begin{codeblock}[language=C]
int idx = threadIdx.x + blockIdx.x * blockDim.x;
\end{codeblock}

\subsection{Grid-stride loops}

The "one-thread, one-element" pattern works well when the number of launched threads matches $N$, but it ties the kernel's correctness to a specific launch configuration. A more flexible idiom is the \textbf{grid-stride loop}: each thread starts at its global index and walks through the array in steps of \texttt{blockDim.x * gridDim.x}, the total number of threads in the grid.

\begin{codeblock}[language=C]
__global__ void vectorAdd(const float* a, const float* b, float* c, int n) {
    int idx    = blockIdx.x * blockDim.x + threadIdx.x;
    int stride = blockDim.x * gridDim.x;
    for (int i = idx; i < n; i += stride)
        c[i] = a[i] + b[i];
}
\end{codeblock}

The kernel now works correctly for \emph{any} grid size: launch a tiny grid and each thread processes many elements; launch a large grid and each thread processes one. This decouples the kernel from the launch configuration and is the recommended idiom in modern CUDA. The course example at \plaintt{cuda/source/vectorAddstride/testStrideNostride.cu} compares the two patterns under three regimes (small vector, large vector with enough threads, large vector with too few blocks) and shows that the strided version stays performant in the under-provisioned case where the non-strided kernel simply does not cover the array.

\begin{observationblock}[Why "grid-stride", not "block-stride"?]
The stride is the number of threads in the entire grid, not just in one block. This makes consecutive iterations of the loop in different threads access \emph{contiguous} memory addresses --- exactly the pattern the GPU coalesces into a single transaction (see section~\ref{sec:cuda-memory}).
\end{observationblock}

The four memory spaces a CUDA programmer normally interacts with are:

\begin{itemize}
    \item \textbf{Global memory}: the off-chip DRAM, the largest space (tens of GB on Ampere) but also the slowest. \textit{Scope}: accessible by all threads of all blocks and grids. \textit{Usage}: \plaintt{cudaMalloc}/\plaintt{cudaMemcpy}.
    \item \textbf{Shared memory}: a small (up to 164\,KB per SM on A100), fast on-chip scratchpad. \textit{Scope}: shared by all threads within a block. \textit{Usage}: declared with the \plaintt{\_\_shared\_\_} qualifier; used to cache data for reuse inside a block (see~\ref{subsec:shared-tiling}).
    \item \textbf{Registers}: the fastest storage on the GPU, mapped to the SM's register file. \textit{Scope}: private to each thread. \textit{Usage}: automatic variables inside a kernel. Spilling to "local" memory (which is really global) happens silently when register pressure is too high, and tanks performance --- watch the compiler report.
    \item \textbf{Constant memory}: a 64\,KB read-only space, cached and optimised for the case where all threads in a warp read the same address. \textit{Scope}: read-only from device code. \textit{Usage}: \plaintt{\_\_constant\_\_} qualifier.
\end{itemize}

\subsection{Coalesced access in practice}

The Ampere memory subsystem services global-memory transactions in 32-, 64- or 128-byte segments. When the threads of a warp request \emph{contiguous} addresses inside a single segment, the hardware merges them into one transaction --- a \textbf{coalesced} access. When the addresses are spread across multiple segments, the hardware issues several transactions and bandwidth utilisation drops accordingly.

\begin{tipsblock}[Memory coalescing]
For optimal performance, threads in a warp should access consecutive memory addresses. Coalesced access can improve bandwidth utilisation by up to $10\times$ compared to non-coalesced patterns.
\end{tipsblock}

The classic counter-example is a transposed access pattern. Reading a row of a matrix (\plaintt{A[row*N + col]}, with \texttt{col} varying with \texttt{threadIdx.x}) is coalesced; reading a column (\plaintt{A[col*N + row]}) is not, because successive threads jump by $N$ floats. The course example at \plaintt{cuda/source/matrixTranspose/matrixTranspose.cu} measures both patterns and shows the bandwidth gap.

\subsection{Shared memory and tiling}
\label{subsec:shared-tiling}

Shared memory shines when the same global-memory value is read by many threads of a block --- which is exactly what happens in matrix multiplication: every element of $A$ contributes to a whole row of $C$, and every element of $B$ to a whole column. The \textbf{tiled matmul} pattern exploits this by loading TILE$\times$TILE blocks of $A$ and $B$ into shared memory cooperatively, reusing them many times, and then advancing along the $K$ dimension.

A trimmed version of the kernel from \plaintt{cuda/source/Global\_Shared\_streaming/matmul\_shared.cu} (\texttt{TILE\_SIZE = 16}):

\begin{codeblock}[language=C]
__global__ void matmul_shared(const float* A, const float* B,
                              float* C, int M, int N, int K) {
    __shared__ float s_A[TILE_SIZE][TILE_SIZE];
    __shared__ float s_B[TILE_SIZE][TILE_SIZE];

    int row = blockIdx.y * TILE_SIZE + threadIdx.y;
    int col = blockIdx.x * TILE_SIZE + threadIdx.x;
    float sum = 0.0f;

    for (int k = 0; k < K; k += TILE_SIZE) {
        s_A[threadIdx.y][threadIdx.x] = A[row*K + k + threadIdx.x];
        s_B[threadIdx.y][threadIdx.x] = B[(k + threadIdx.y)*N + col];
        __syncthreads();                      // tile fully loaded

        for (int i = 0; i < TILE_SIZE; ++i)
            sum += s_A[threadIdx.y][i] * s_B[i][threadIdx.x];
        __syncthreads();                      // before overwriting
    }
    if (row < M && col < N) C[row*N + col] = sum;
}
\end{codeblock}

Two ideas are at play here. The cooperative load amortises each global-memory read over \texttt{TILE\_SIZE} multiply-adds, turning a memory-bound kernel into a compute-bound one. And the two \texttt{\_\_syncthreads()} barriers separate the two phases of the loop body: \emph{all} threads must finish loading the tile before \emph{any} thread starts using it, and \emph{all} threads must finish using it before \emph{any} thread overwrites it on the next iteration.

\begin{warningblock}[Shared memory bank conflicts]
Shared memory is split into 32 \textit{banks}; an access by a warp is conflict-free only if at most one thread accesses each bank (or all threads access the same address, which is broadcast). A common cause of conflicts is column-major access into a 32-wide shared array; the standard fix is to over-pad the array (e.g.\ \plaintt{\_\_shared\_\_ float s[32][33]}) so that successive columns fall into different banks.
\end{warningblock}

\subsection{Host memory: pageable, pinned, managed}

Allocations on the \emph{host} side also have a performance dimension. The runtime offers three flavours:

\begin{itemize}
    \item \textbf{Pageable} memory --- ordinary \plaintt{malloc}/\plaintt{new}. The OS may page it out, so before each \plaintt{cudaMemcpy} the runtime has to copy the buffer into an internal pinned staging area. This double-copy roughly halves the achievable PCIe bandwidth.
    \item \textbf{Pinned} (page-locked) memory --- allocated with \plaintt{cudaMallocHost} or \plaintt{cudaHostAlloc}. The OS cannot page it out, so the GPU's DMA engine reads directly from it. Transfer bandwidth is typically $1.5\times$--$2\times$ that of pageable memory, and pinned buffers are a prerequisite for \emph{asynchronous} \plaintt{cudaMemcpyAsync} (see section on streams).
    \item \textbf{Managed} memory --- allocated with \plaintt{cudaMallocManaged}. A single virtual address is valid on both host and device; the driver migrates pages on demand. Convenient (one allocator, no explicit \plaintt{cudaMemcpy}) but the migration is implicit, which makes performance harder to predict.
\end{itemize}

\begin{codeblock}[language=C]
float *pageable = (float*)malloc(bytes);              // CPU only
float *pinned;   cudaMallocHost(&pinned, bytes);      // page-locked
float *managed;  cudaMallocManaged(&managed, bytes);  // unified
\end{codeblock}

The course example at \plaintt{cuda/source/vecAdd\_pinnedpeageble/vecAdd\_managed.cu} (the directory name is a typo for "pinned/pageable") benchmarks pageable vs.\ pinned transfers side-by-side; the managed version lives at \plaintt{cuda/source/vecAddtion\_managed/vecAdd\_managed.cu}.

\subsection{Unified memory and page faults}

When a kernel touches a managed-memory page that is currently resident on the host, the GPU raises a \textbf{page fault}: execution stalls, the driver migrates the page over PCIe, and only then does the kernel resume. The first kernel after an allocation pays this cost on every page; subsequent kernels see the data already on the device and run at full speed.

To avoid surprises, CUDA exposes two hint APIs:
\begin{itemize}
    \item \plaintt{cudaMemPrefetchAsync(ptr, size, deviceId)} --- asynchronously migrate a range to a target device (use \plaintt{cudaCpuDeviceId} for the host) before it is needed. This is the cheapest way to make managed memory perform like an explicit \plaintt{cudaMemcpy}.
    \item \plaintt{cudaMemAdvise(ptr, size, advice, deviceId)} --- tell the driver about an access pattern, e.g.\ \plaintt{cudaMemAdviseSetReadMostly} or \plaintt{cudaMemAdviseSetPreferredLocation}. The driver uses these as scheduling hints, not as commands.
\end{itemize}

\begin{exampleblock}[Prefetching managed buffers before launch]
\begin{codeblock}[language=C]
cudaMallocManaged(&a, size);
cudaMallocManaged(&b, size);
cudaMallocManaged(&c, size);

cudaMemPrefetchAsync(a, size, deviceId);   // warm the GPU
cudaMemPrefetchAsync(b, size, deviceId);
cudaMemPrefetchAsync(c, size, deviceId);

addVectors<<<blocks, threads>>>(c, a, b, N);
cudaDeviceSynchronize();

cudaMemPrefetchAsync(c, size, cudaCpuDeviceId);  // bring result home
\end{codeblock}
This is the pattern used in \plaintt{cuda/solution/04-stream/stream1.cu}.
\end{exampleblock}

\section{Asynchronous Execution and CUDA Streams}

So far we have launched kernels on the implicit \textit{default stream}: every operation issued by the host is appended to a single FIFO queue and executed in order. The default stream is convenient but it forbids exactly the kind of overlap a GPU can exploit --- copying the next batch of data while the current batch is being processed, or running independent kernels side by side.

A \textbf{CUDA stream} is just an ordered queue of operations. Operations within a stream execute in order; operations in \emph{different} streams may run concurrently if the hardware has the resources for it. Creating, using and destroying a stream is straightforward:

\begin{codeblock}[language=C]
cudaStream_t stream;
cudaStreamCreate(&stream);

someKernel<<<numberOfBlocks, numberOfThreads, 0, stream>>>();   // 4th launch arg

cudaStreamDestroy(stream);
\end{codeblock}

    \centering
    \includegraphics[width=0.8\textwidth]{assets/cuda-stream.png}
    \caption{Concurrent execution of kernels and transfers using multiple streams.}
    \label{fig:cuda-streams}
\end{figure}

\subsection{Overlapping H2D, kernel and D2H}

The motivating use case for streams is the classical pipeline: split a large array into chunks, and for each chunk overlap the host-to-device copy of one chunk with the kernel execution of the previous chunk and the device-to-host copy of the chunk before that. This requires two ingredients:
\begin{itemize}
    \item a non-blocking copy primitive --- \plaintt{cudaMemcpyAsync(dst, src, n, kind, stream)}, which enqueues the transfer on \texttt{stream} and returns immediately;
    \item \emph{pinned} host memory, otherwise the runtime cannot DMA directly and silently downgrades the call to a synchronous copy.
\end{itemize}

\begin{codeblock}[language=C]
const int nStreams = 4, chunk = N / nStreams;
cudaStream_t s[nStreams];
for (int i = 0; i < nStreams; ++i) cudaStreamCreate(&s[i]);

for (int i = 0; i < nStreams; ++i) {
    int off = i * chunk;
    cudaMemcpyAsync(d_x + off, h_x + off, chunk*sizeof(float),
                    cudaMemcpyHostToDevice, s[i]);
    kernel<<<blocks, threads, 0, s[i]>>>(d_y + off, d_x + off, chunk);
    cudaMemcpyAsync(h_y + off, d_y + off, chunk*sizeof(float),
                    cudaMemcpyDeviceToHost, s[i]);
}
for (int i = 0; i < nStreams; ++i) cudaStreamDestroy(s[i]);
\end{codeblock}

The course solution at \plaintt{cuda/solution/04-stream/stream1.cu} applies the same idea to a vector-addition workload, using \plaintt{cudaMallocManaged} + \plaintt{cudaMemPrefetchAsync} on three streams to overlap the initialisation of \texttt{a}, \texttt{b} and \texttt{c} before adding them.

\subsection{Synchronisation: do not over-synchronise}

Streams give the GPU permission to overlap work; you still need synchronisation to know when results are safe to read on the host. Two primitives cover most cases:

\begin{itemize}
    \item \plaintt{cudaStreamSynchronize(stream)} --- block the host until \emph{this} stream has drained. Other streams keep running.
    \item \plaintt{cudaDeviceSynchronize()} --- block until \emph{all} streams on the current device have drained. Heavy-handed, but necessary at the very end of a phase or before tearing down resources.
\end{itemize}

A common mistake is to scatter \plaintt{cudaDeviceSynchronize()} between operations "to be safe": each call effectively serialises the GPU and makes streams pointless. Prefer per-stream synchronisation, and let the runtime keep operations from \emph{different} streams overlapping.

\begin{tipsblock}[Stream callbacks and events]
For finer-grained synchronisation, CUDA also exposes \plaintt{cudaEvent\_t} (timestamps that can be recorded into a stream and queried/waited on later) and \plaintt{cudaStreamAddCallback} (a host function fired when the stream reaches that point). Events are also the right tool for measuring kernel execution time, as in the \plaintt{matmul\_shared.cu} example.
\end{tipsblock}

\begin{advancedblock}[Non-blocking streams]
\plaintt{cudaStreamCreate} creates a stream that synchronises with the default (legacy) stream. The \plaintt{cudaStreamCreateWithFlags(\&s, cudaStreamNonBlocking)} variant decouples it from the default stream, which is preferable when mixing default-stream code (e.g.\ from a library) with explicitly-managed streams. Not covered in detail in this course.
\end{advancedblock}

\section{Profiling Workflow}

A typical optimisation cycle on the GPU starts from a CPU baseline and proceeds in two passes: first a \emph{system-wide} profile to understand where time is spent (CPU vs.\ GPU, transfer vs.\ compute, idle gaps in the timeline), then a \emph{per-kernel} deep-dive on the worst offender. The two NVIDIA tools that map onto these passes are:

\begin{itemize}
    \item \textbf{Nsight Systems} (\plaintt{nsys}) --- a low-overhead system-level tracer. It produces a timeline showing kernels, memory transfers, OS-level CPU activity and (optionally) MPI / NVTX ranges. This is what you look at first to confirm that the GPU is busy when it should be and that transfers are overlapping with compute.
    \item \textbf{Nsight Compute} (\plaintt{ncu}) --- a per-kernel hardware-counter profiler. It reports occupancy, achieved memory bandwidth, instruction mix, warp stall reasons and many other metrics, but at the cost of replaying each kernel several times. Use it after Nsight Systems has identified the kernel that matters.
\end{itemize}

\subsection{Capturing a profile}

The minimal Nsight Systems invocation traces CUDA and NVTX activity and writes a \plaintt{.nsys-rep} file that the \plaintt{nsys-ui} GUI (or \plaintt{nsys stats}) can open later:

\begin{codeblock}[language=bash]
nsys profile -t cuda,nvtx --stats=true --force-overwrite=true \
             -o report ./my_program
\end{codeblock}

The \plaintt{-t} flag selects which traces to collect (add \plaintt{mpi} or \plaintt{openacc} as needed); \plaintt{--stats=true} prints a summary on the console after the run, which is usually enough for a first triage.

For a full per-kernel report, switch to Nsight Compute:

\begin{codeblock}[language=bash]
ncu --set full -o report ./my_program
\end{codeblock}

The \plaintt{--set full} preset enables every metric group; cheaper presets like \plaintt{--set basic} or \plaintt{--set roofline} are available when only a subset is needed. Both tools require write access to GPU performance counters; on Leonardo this is granted automatically inside a \plaintt{boost\_usr\_prod} job.

\subsection{Annotating the timeline with NVTX}

Without help, an Nsight Systems timeline is a sea of unnamed CUDA API calls. The \textbf{NVIDIA Tools Extension} (NVTX) library lets you mark regions of host code so that they appear as named ranges on the timeline, which makes correlating profile features with source code trivial. The pattern is just push/pop:

\begin{codeblock}[language=C]
#include <nvtx3/nvToolsExt.h>

nvtxRangePushA("H2D Transfer");
cudaMemcpy(d_A, A, bytes, cudaMemcpyHostToDevice);
cudaMemcpy(d_B, B, bytes, cudaMemcpyHostToDevice);
nvtxRangePop();

nvtxRangePushA("MatMul Kernel (Shared Memory)");
matmul_shared<<<grid, block>>>(d_A, d_B, d_C, M, N, K);
cudaDeviceSynchronize();
nvtxRangePop();
\end{codeblock}

This snippet is condensed from \plaintt{cuda/source/Global\_Shared\_streaming/matmul\_shared.cu}, where every phase (H2D, kernel, D2H, CPU computation) is wrapped in its own NVTX range. The corresponding \plaintt{.nsys-rep} files in that directory show exactly how the labelled bands stack up on the timeline.

\subsection{What to look at first}

\begin{tipsblock}[Profiler triage checklist]
\begin{enumerate}
    \item \textbf{Is the GPU busy?} On the Nsight Systems timeline, a wide band of GPU activity is good; large idle gaps between kernels usually mean over-synchronisation on the host or too few streams.
    \item \textbf{Transfers vs.\ compute.} If the H2D / D2H bands are as wide as the kernel band, the kernel is transfer-bound: pin host memory, use \plaintt{cudaMemcpyAsync} on streams, or move to managed memory with prefetching.
    \item \textbf{Kernel duration.} Once the timeline looks healthy, sort kernels by total time and pick the heaviest one for an Nsight Compute deep-dive.
    \item \textbf{Inside Nsight Compute}: check \emph{achieved occupancy} (low values point at register or shared-memory pressure), \emph{memory throughput} as a fraction of peak (low values mean uncoalesced access or insufficient ILP), and the \emph{warp stall reason} histogram (memory dependency, execution dependency, etc.).
\end{enumerate}
\end{tipsblock}

\begin{observationblock}[A note on the roofline model]
A complementary --- and more quantitative --- way to read these metrics is the \textit{roofline model}, which plots achieved performance against arithmetic intensity (FLOPs per byte) and bounds it by the peak compute and peak memory-bandwidth lines. We do not develop it here; the \plaintt{ncu --set roofline} preset already produces the plot for any kernel.
\end{observationblock}

\section{GPU programming with OpenMP target offload}

CUDA gives the programmer full control over the GPU but also full responsibility for managing devices, memory, kernels and streams; and the resulting code is bound to NVIDIA hardware. \textbf{OpenMP target offload} (introduced in OpenMP 4.0 and consolidated in 4.5/5.x) takes the opposite trade-off: a small set of pragmas asks the compiler to move a region of code and the data it needs to an attached accelerator, while the rest of the program stays in standard C/C++/Fortran. The same source can be retargeted to a different GPU vendor or fall back to the CPU by changing only compiler flags --- at the price of less direct control over the hardware.

This section walks through the constructs that the OpenMP school examples (\plaintt{GPU/OpenMP\_2024/}) exercise, in roughly the same order: \emph{target} first, then \emph{teams/threads}, then data mapping, then asynchrony, then multi-GPU.

\subsection{The target construct}

The basic block is \plaintt{\#pragma omp target}: it marks a structured region whose statements should execute on the device. Scalars and array sections referenced inside the region are mapped to the device automatically (with \plaintt{tofrom} semantics for arrays, more on this below). The course's \plaintt{Simple/simple0.c} uses it just to query the GPU:

\begin{codeblock}[language=C]
if (omp_get_num_devices() == 0) {
    printf("No accelerator found\n"); exit(1);
}

#pragma omp target device(0)
{
    int nteams   = omp_get_num_teams();
    int nthreads = omp_get_max_threads();
    printf("device 0: %d teams, %d threads/team\n", nteams, nthreads);
}
\end{codeblock}

Without further directives the compiler runs the body on a \emph{single} team with a \emph{single} thread --- functionally correct, but only a tiny fraction of the GPU is used. To get parallelism we need to combine \plaintt{target} with the team/thread constructs.

\subsection{Teams, threads and the SIMT mapping}

OpenMP exposes three nested levels of parallelism that map onto the GPU thread hierarchy:

\begin{itemize}
    \item a \textbf{league} of \textbf{teams} (\plaintt{\#pragma omp teams}) --- each team becomes a CUDA thread block;
    \item a team's \textbf{threads} executing a worksharing loop (\plaintt{distribute parallel for}) --- each thread becomes a CUDA thread inside the block;
    \item optionally, \textbf{SIMD lanes} inside a thread (\plaintt{simd}) --- which on the GPU lines up with how a warp executes a SIMT instruction.
\end{itemize}

The composite construct that one sees most often in practice is

\begin{codeblock}[language=C]
#pragma omp target teams distribute parallel for simd \
        map(to: a, n, x[0:n]) map(tofrom: y[0:n])
for (int i = 0; i < n; ++i)
    y[i] = a * x[i] + y[i];
\end{codeblock}

which is the SAXPY kernel from \plaintt{VectorMultiplications/saxpi.gpu.simple.c}. Reading the directives outside-in: the \plaintt{target} sends control to the device; \plaintt{teams} creates a league of thread blocks; \plaintt{distribute} hands successive chunks of loop iterations to successive teams; \plaintt{parallel for} parallelises within each team; and \plaintt{simd} hints at vectorisation inside a thread.

The number of teams and threads can be left to the compiler or controlled with the \plaintt{num\_teams}, \plaintt{thread\_limit}, \plaintt{num\_threads} and \plaintt{dist\_schedule} clauses. The example progression \plaintt{saxpi.gpu.v0.c} $\to$ \plaintt{v2.c} explores this experimentally:

\begin{itemize}
    \item v0: 1 team, 1 thread --- correct, painfully slow (left as a baseline).
    \item v1: a single tunable team count; throughput grows roughly with the number of teams up to the SM count.
    \item v2: full control over both axes via \plaintt{num\_teams(ial)} and \plaintt{num\_threads(itr)} with \plaintt{dist\_schedule(static, itr)}; performance is best when the team count saturates the SMs and the thread count is a multiple of 32 --- the same warp-friendly constraint we saw in CUDA.
\end{itemize}

\begin{tipsblock}[Rule of thumb]
Letting the compiler pick \plaintt{num\_teams} and \plaintt{thread\_limit} is usually within $10$--$20\%$ of the hand-tuned configuration. Do not micro-tune these clauses unless the profiler says the kernel is launch-bound or you have a specific layout in mind.
\end{tipsblock}

\subsection{Data mapping and persistent device data}

By default, every \plaintt{target} region copies the data it touches onto the device on entry and back on exit. This is safe but expensive: in an iterative algorithm the same arrays bounce across PCIe on every iteration. The \plaintt{map} clause makes the intent explicit and lets the runtime optimise:

\begin{itemize}
    \item \plaintt{map(to: A[0:n])} --- copy host $\to$ device on entry, do not copy back;
    \item \plaintt{map(from: A[0:n])} --- allocate on device, copy device $\to$ host on exit;
    \item \plaintt{map(tofrom: A[0:n])} --- both directions (the implicit default for arrays);
    \item \plaintt{map(alloc: A[0:n])} --- allocate on device, no transfer in either direction.
\end{itemize}

For arrays that survive across multiple kernels, the right tool is a \plaintt{target data} region (structured) or a pair of \plaintt{target enter data} / \plaintt{target exit data} directives (unstructured), which decouple the data lifetime from any particular kernel. The course's GEMV progression illustrates the pay-off. Version~1 maps the matrix on every call:

\begin{codeblock}[language=C]
void gemv(float alpha, float* A, float* x, float beta, float* y,
          size_t rows, size_t cols) {
    #pragma omp target teams distribute \
            map(to: A[0:rows*cols], x[0:cols], alpha, beta) \
            map(from: y[0:rows])
    for (size_t i = 0; i < rows; ++i) { /* ... */ }
}
\end{codeblock}

Version~3 hoists the allocation out of the kernel by attaching it to the array's lifetime:

\begin{codeblock}[language=C]
float* allocate_and_initialize_array(size_t rows, size_t cols) {
    float* a = (float*)malloc(rows*cols*sizeof(float));
    /* ... initialise on the host ... */
    #pragma omp target enter data map(to: a[:rows*cols])
    return a;
}

void deallocate(float* a, size_t n) {
    #pragma omp target exit data map(delete: a[:n])
    free(a);
}
\end{codeblock}

The kernel itself now runs without per-call mapping, and a final \plaintt{\#pragma omp target update from(y[:rows])} brings the result back. On a $32{,}768 \times 32{,}768$ GEMV this turns a transfer-bound run into a compute-bound one.

\subsection{Asynchronous offload and OpenMP "streams"}

A target region without further annotation is synchronous: the host blocks until the kernel finishes. The \plaintt{nowait} clause turns it into an OpenMP \emph{task} that runs asynchronously, and the host can continue with other work --- including launching more target tasks. \plaintt{taskwait} (or \plaintt{depend} clauses for fine-grained ordering) re-synchronises.

The course example \plaintt{Asyncomputing/multiple.streams.c} simulates CUDA streams entirely with tasks: it splits an array into chunks and fires one asynchronous \plaintt{target} per chunk inside an \plaintt{omp single} region:

\begin{codeblock}[language=C]
#pragma omp parallel
{
    #pragma omp single
    {
        for (int s = 0; s < num_streams; ++s) {
            int start = s * chunk_size;
            int end   = (s == num_streams - 1) ? N : start + chunk_size;
            #pragma omp task firstprivate(start, end) nowait
            gpu_task(data, start, end);   // contains a #pragma omp target
        }
    }
    #pragma omp taskwait
}
\end{codeblock}

Each task carries its own target region; the runtime is free to schedule them on different CUDA streams under the hood, giving the same overlap of transfers and kernels as explicit \plaintt{cudaMemcpyAsync} would.

\subsection{Multi-GPU offload}

A node like Leonardo has four A100s; OpenMP exposes them as device IDs $0,\,1,\,\dots,\,N{-}1$. Two ingredients are needed to use more than one:
\begin{itemize}
    \item the \plaintt{device(d)} clause on \plaintt{target} / \plaintt{target data} / \plaintt{target enter data}, which selects the GPU that the construct will run on;
    \item the \plaintt{\#pragma omp declare target} directive, which marks a function (or variable) as callable from device code so that the same routine can be reused across GPUs.
\end{itemize}

The dual-GPU SAXPY in \plaintt{ModularProgramming/saxpi.dualgpu.simple.c} packages the per-GPU kernel into a \plaintt{declare target} function and dispatches it to a chosen device:

\begin{codeblock}[language=C]
#pragma omp declare target
int computeLoop(int n, float a, const float *x, float *y, int dev) {
    #pragma omp target data device(dev) \
            map(to: a, n, x[0:n]) map(tofrom: y[0:n])
    {
        #pragma omp target teams distribute parallel for simd device(dev)
        for (int i = 0; i < n; ++i)
            y[i] = a * x[i] + y[i];
    }
    return dev;
}
#pragma omp end declare target
\end{codeblock}

Splitting work across GPUs is then just a matter of partitioning the index range and calling \plaintt{computeLoop} once per device --- typically inside an \plaintt{omp parallel} so the host issues launches on multiple GPUs concurrently.

\subsection{Compilers and Leonardo}

Three compilers support OpenMP target offload to NVIDIA GPUs; the syntax is the same, only the flags change.

\begin{codeblock}[language=bash]
# NVIDIA HPC SDK
nvc -mp=gpu -gpu=cc80 -O3 -fast -Minfo=all -o prog prog.c

# Clang
clang -fopenmp -fopenmp-targets=nvptx64 \
      -Xopenmp-target -march=sm_80 -o prog prog.c

# GCC offload
gcc -fopenmp -foffload=nvptx-none \
    -foffload-options="-march=sm_80" -o prog prog.c
\end{codeblock}

On Leonardo the recipe documented at \plaintt{GPU/OpenMP\_2024/resources/HOWTO\_compile.md} is

\begin{codeblock}[language=bash]
module load nvhpc/24.3 openmpi/4.1.6--nvhpc--24.3

OMP_FLAG="-mp=multicore,gpu"      # OpenMP on both CPU and GPU
GPU_FLAG="-gpu=cc80 -target=gpu -gpu=nomanaged"

nvc -O3 -fast -Minfo=all $GPU_FLAG $OMP_FLAG prog.c -o prog
\end{codeblock}

A few environment variables are worth knowing about:
\begin{itemize}
    \item \plaintt{OMP\_TARGET\_OFFLOAD=MANDATORY} --- abort if offload is not available, instead of silently falling back to the CPU. Use this in benchmarks.
    \item \plaintt{OMP\_NUM\_TEAMS}, \plaintt{OMP\_TEAM\_LIMIT} --- runtime override for the team count and the maximum threads per team.
    \item \plaintt{OMP\_DISPLAY\_ENV=true} --- prints the OpenMP runtime configuration on startup; useful when you suspect an environment misconfiguration.
\end{itemize}

\section{CUDA, OpenMP target, and what comes next}

Looking back at the chapter, the two programming models we have seen sit at opposite ends of the productivity / control trade-off. CUDA exposes the hardware almost directly: the programmer chooses the launch configuration, places data in shared memory, schedules transfers on streams, picks pinned versus managed allocations. The reward is full performance and full responsibility, locked to the NVIDIA stack. OpenMP target offload hides most of those decisions behind a handful of pragmas: the same loop annotated with \plaintt{target teams distribute parallel for} delivers a respectable fraction of the CUDA performance on the same A100, and could in principle be retargeted to a different vendor by changing only compiler flags.

A third directive-based model, \textbf{OpenACC}, occupies roughly the same niche as OpenMP target but with a slightly different vocabulary (\plaintt{parallel}/\plaintt{kernels}, \plaintt{gang}/\plaintt{worker}/\plaintt{vector}, \plaintt{copyin}/\plaintt{copyout}) and a stronger focus on incremental porting of existing scientific codes. OpenACC is the subject of chapter~7, which also includes a side-by-side comparison of the OpenACC and OpenMP directives and clauses, and a Laplace-equation case study that walks the same algorithm through both ecosystems.
